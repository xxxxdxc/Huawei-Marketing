# 平台门店营销规则

本次调整仅涉及后端写作策略与资料边界，前端设置页、Brief核心职责、卖点确认及默认模型调用次数不变。

## 当前行为

| 平台 | 默认门店策略 | 资料缺失 |
|---|---|---|
| 微信公众号 | 产品宣传，自然收尾；`cta`可以为空。不输出所在门店、销售联系、预约或到店引导 | 不因没有门店资料追问 |
| 小红书 | 产品正文后，在根级`cta`自然介绍销售人员所在门店，再给咨询引导 | 使用简短通用门店引导，不阻塞 |
| 朋友圈 | 同样在根级`cta`承接门店，表达更精简 | 使用简短通用门店引导，不阻塞 |

公众号允许用户明确要求加入门店营销作为例外。原需求只有门店信息、通用到店目标，或从其他平台继承的目标，不自动成为公众号例外。平台切换时重新计算当前平台规则，保留产品卖点和证据，不重跑Brief。对话中的原平台、切换记录与用户原话用于核对例外适用范围。

## 输入与保存

用户在本次任务自然语言中提供门店名称、位置、联系方式、营业时间或明确的服务。沿用Brief的`user_constraints`承载原话；既有Writer大纲调用额外提取可选`store_context`，不新增模型调用。

`store_marketing_context`保存在任务中：

```json
{
  "details": [
    {
      "field": "name",
      "value": "杭州湖滨店",
      "evidence": {"turn_id": "U1", "quote": "我的门店名称是杭州湖滨店"}
    }
  ],
  "wechat_exception": null
}
```

`field`可为`name/location/contact/hours/service`。每个值必须逐字存在于证据quote，quote必须对应真实用户轮次；不能采用知识库、模型策略或平台切换的自动说明作为门店资料/新授权。无信息时允许空details。提取值无来源时，大纲被拒绝并保留诊断，不进入正文。

这些是用户提供的业务资料，独立于产品Fact Cards；不分配Fact ID、不声称通过ima核验。用户必须提供的门店身份/联系等约束不要求用产品事实卡承接；含产品参数、优惠等混合要求仍保留原证据门槛。用户要求必须写具体信息但缺失时，由现有Brief追问机制处理；已补充适配规则，无额外设置界面。

## 三阶段与核验

- 大纲阶段提供用户原话、已存资料及当前平台初始策略；程序校验提取和例外后，保存最终上下文。
- 正文与修订根据`store_marketing_policy`执行；门店信息集中结尾，不逐段插入到店试验或核对话语。
- 公众号结构允许空CTA，最终Document原本就允许空串；旧版Planner草稿字段保持兼容。
- 新写稿设置`store_marketing_version=platform_store_v1`。独立Reviewer获得相同门店上下文，核对来源和平台约束；程序同时检查明确的门店泄露和缺少门店结尾，走现有一次修订再完整复核。
- 已保存的旧稿不会自动补广告或删除原结尾。只有重新写稿时才启用新版本策略。

不虚构门店地址、服务、库存、优惠或体验设备。用户业务资料的逐字校验只证明来源，不能独立证明现实经营情况；对外文案不能由这些资料推导新的产品能力或门店承诺。程序措辞检查不覆盖全部语义变体，最终仍结合独立核验。

实现入口：`backend/store_marketing.py`、`backend/platform_writer.py`、`backend/writer_skills.md`。专项回归：`backend/test_store_marketing.py`。本轮使用隔离模型响应验证工作流，不消耗额度追加真实模型对照，不将测试通过称为真实成稿质量提升。
